# Production readiness audit

**Date:** 2026-08-10  
**Scope:** `frontend/` (Next.js 16 / TypeScript), `backend/` (FastAPI / Python 3.12), Compose, CI, configuration, and repository hygiene.  
**Conclusion:** The hardening changes in this review remove the immediately exploitable issue found, but the product is **not yet ready to be called production-ready**. The remaining P1 items below need to be scheduled before a broad public release.

This is a source, configuration, and static UI review. It is not a penetration test. Browser-driven visual testing could not be run in this workspace because the browser-control runtime failed to start; the UI observations are therefore explicitly static-review findings.

## Codebase and architecture assessment

The main application boundary is sound: the web app and API are separate and the backend generally resolves an organization context before data access. The current pass strengthens that boundary at scheduled jobs, forwarded headers, auth redirects, JWT issuer validation, and operational configuration.

Production-ready structure should now be maintained as follows:

- `frontend/src/app` owns routes and route handlers; `frontend/src/features` owns feature UI; `frontend/src/lib` owns API/auth helpers; `frontend/src/proxy.ts` owns the Next request gate.
- `backend/app/api` owns HTTP concerns; `backend/app/services` owns domain work; `backend/app/core` owns configuration, security, middleware, and request metadata; `backend/tests` owns boundary regression tests.
- `docs/reviews` owns dated audit evidence and the remediation loop. It should not become a replacement for product PRDs.
- Compose only orchestrates the deployed application services; Supabase remains an external managed dependency. Secrets stay in deployment configuration, never in committed `.env` files.

The remaining architectural decision with the greatest security impact is SEC-01: move browser-to-backend authentication behind a BFF boundary. Do that before adding more privileged browser features.

## UI and user-experience assessment

The static UI audit found a coherent base: a task-oriented financial workspace, reusable primitives, clear sidebar grouping, visible demo treatment, and a design-token system that supports dark surfaces. The Impeccable static anti-pattern detector reported no violations.

The experience is strongest on dense desktop information work. It needs a deliberate mobile and failure-state pass before claiming inclusive, production-grade usability:

| Accessibility         | Baseline components expose labels/focus patterns, but no automated keyboard, screen-reader, contrast, or target-size evidence exists. | Complete QLT-01 and UX-02/03.                                    |
